# Change: Dedupe the supplier/customer portal shells into the shared portal composition layer

## Why

`refactor-customer-portal-for-portal-symmetry` built a composition layer (`PortalContextCore` behind thin typed facades, `PortalPanelConfigurator`, `UsePanelSession`, `ResolvesPanelContext`) precisely so a second portal could be composed, not copied. The supplier portal shell (Slice 2, `75288c1`) copied anyway: `SupplierPanelProvider` is a string-swap clone of `CustomerPanelProvider` (~90 duplicated lines each of brand resolvers + the `switchPortalCompany` user-menu action, and it renders the customer-namespaced `filament.customer.brand-logo` view inside the supplier panel), `AcceptPortalInvitation` (165 lines), the login page (75 lines), and the invite action (62 lines) are near-verbatim pairs. The clones have already diverged once with a security consequence — the supplier accept page filtered invitation tokens by portal while the cloned-from customer page did not (fixed in `01494e5`), and `InviteSupplierPortalUser` guards `is_supplier` while `InvitePortalUser` gained its `is_buyer` guard only in the same fix. Every further portal slice widens the gap; the catalog registration work is adding portal surfaces now.

## What Changes

- **DP-1 Panel branding/menu into the configurator**: `PortalPanelConfigurator` gains the shared branding resolvers (brand name, logo, favicon — all resolved from the portal context's company/team with the existing `Throwable` guard) and the `switchPortalCompany` user-menu action, parameterized by the portal's context service and dashboard class. Both providers shrink to panel id/domain/guard/discovery + one configurator call. The brand-logo Blade view moves to a shared `filament/portal/brand-logo.blade.php`; the supplier panel stops rendering a customer-namespaced view.
- **DP-2 One accept flow**: the byte-identical `accept()` transaction (user lookup/create, `CompanyPortalUser::updateOrCreate`, `markAccepted`) moves to `app/Actions/Portal/AcceptPortalInvitation`; it is already portal-agnostic since everything derives from `PortalInvitation` (including `portal`). The two Filament pages keep only mount/form/headings/redirect and both filter the token lookup by their own `PortalType` (customer side fixed in `01494e5`; this change pins it in the spec for both portals).
- **DP-3 One invite path**: `InvitePortalUser` and `InviteSupplierPortalUser` collapse into a single portal-parameterized action that validates the company role for the target portal (`is_buyer`/`is_supplier`), deletes stale same-portal invitations, and sends one `PortalUserInvitationMail` whose subject/URL/copy derive from `$invitation->portal`. `SupplierPortalUserInvitationMail` and its Blade view are removed; the mail view is parameterized the same way.
- **DP-4 Finish the naming symmetry**: `User::hasActiveBuyerPortalAccess()` → `hasActiveCustomerPortalAccess()` (completing the half-rename from CP-1; the supplier twin already follows this convention).
- **DP-5 Supplier ownership helper in the shared concern**: `ResolvesPanelContext` gains `userOwnsSupplierCompany()` mirroring `userOwnsBuyerCompany()`; `SupplierArticlePolicy::ownsRow()` (and the Slice 3 supplier RFQ policies) consume it instead of private reimplementations.

No behavior change except: supplier panel favicon/brand-logo now come from the shared view (identical markup), and both portals' invitation-token scoping becomes a spec requirement rather than an implementation accident.

Out of scope (deliberately): staff-side supplier portal-user management parity (a `PortalUsersRelationManager` for suppliers is a feature, not a dedup); the public catalog / portal registration surfaces (active `add-public-product-catalog` change); merging the per-panel login/accept *page classes* themselves (kept as thin per-panel classes so panel discovery, slugs, and `$withoutRouteMiddleware` stay explicit — see design.md).

## Impact

- Affected specs: `customer-portal` (MODIFIED: Customer Portal Branding, Customer Portal User Access), `supplier-portal` (MODIFIED: Supplier Portal Panel, Supplier Portal Access via Invitations)
- Affected code: `app/Providers/Filament/{Customer,Supplier}PanelProvider.php`, `app/Support/PortalPanelConfigurator.php`, `app/Filament/{Customer,Supplier}/Pages/AcceptPortalInvitation.php`, `app/Filament/{Customer,Supplier}/Pages/Auth/*Login.php`, `app/Actions/{CustomerPortal,SupplierPortal}/Invite*.php` → `app/Actions/Portal/`, `app/Mail/PortalUserInvitationMail.php` (parameterized) / `SupplierPortalUserInvitationMail.php` (removed), `app/Models/User.php` (rename), `app/Policies/Concerns/ResolvesPanelContext.php`, `app/Policies/SupplierArticlePolicy.php` + Slice 3 supplier policies, `resources/views/filament/{customer → portal}/brand-logo.blade.php`, `resources/views/emails/*portal-user-invitation*`
- Tests: `tests/Feature/CustomerPortal/**` and `tests/Feature/SupplierPortal/**` must stay green (they pin behavior through the dedup); invite/accept tests move to shared-action coverage plus per-portal wiring assertions
- **Depends on**: `add-public-product-catalog` archiving first (its supplier-portal spec is the base these deltas modify, and its uncommitted portal surfaces touch the same files)
